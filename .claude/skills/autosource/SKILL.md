# AutoSource — 数据源自动发现

**目标是发现该领域下各种成体系的公开信息载体**——既包括"整理好的资源集合"（列表 / 数据库 / 合集 / 排名 / 标准文件），也包括"权威的内容入口"（官方文档站、技术手册、知识库、API 文档、帮助中心、论文库）。数据集只是其中一类，不应占主导。

输入 `/autosource <领域描述>`，执行一条线性流程：

```
初始化（预留运行目录） → 0 领域拆解 → 1 知识清单 → 2 验证搜索 → 3 增量发现 → 4 覆盖评估与扩量 → 5 写入 raw.json → 6 收尾
```

流程中间没有交接停靠点——运行到最后一步（阶段 6 收尾）才算结束，任何一个中间环节都不是终点。

## 分工与边界

**分工原则**：LLM 只负责语义环节（领域拆解、知识清单、搜索、验证与提取判断），一切确定性环节（时间戳、目录命名、证据校验、清单并入、去重、CSV 编码、stats 统计、搜索日志、文件清理）由脚本保证。raw.json 由本流程按契约用 Write 直接落盘（阶段 5）。

**运行期边界**：本流程不写代码、不跑测试——运行中禁止调用开发类技能；唯一合法的 Bash 是 postprocess 命令（初始化 `--prepare` 与阶段 6 收尾）。

## 参数与运行约定

| 参数 | 必填 | 说明 |
|------|------|------|
| `<领域描述>` | 是 | 粗粒度文本，如 `算力服务器` |
| `-c` | 否 | 预设分类路径，如 `-c "GPU服务器" "CPU服务器"` |

- **领域词**：从领域描述中提炼核心关键词，空格替换为 `_`，作为 raw.json 的 domain 字段。
- **输出目录**：流程开始时脚本预留 `outputs/run_{时间戳}/`（每次运行唯一），收尾时重命名为 `outputs/{领域词}_{时间戳}/` 并生成交付物——最终产物位置以收尾 stdout 的"输出目录"为准。

示例：输入 `帮我收集用于AI训练的GPU算力服务器相关数据源` → 目录 `outputs/算力服务器_2026-08-12-143000/`。

## 通用纪律

### 搜索词构造

构造搜索关键词的核心词类（自由角度的完整角度类别见阶段 3 角度池）：

1. **组织形式词**：包括但不限于数据库、排名、列表、标准、仓库、数据集、文献库、合集等。
2. **体裁 / 入口词**：包括但不限于官方文档、开发者文档、technical documentation、手册、知识库、API 参考、帮助中心、白皮书、论文文献、专利、市场研究等。
3. **来源角色词**（回答"谁发布的"）：标准组织、监管机构、政府部门、行业协会、厂商、研究机构、大学、评测机构、基金会、公共数据平台等——用于自由角度与扩量轮补搜。
4. **厂商 / 产品名**（按意图区分）：不裸搜产品名、不搜单个产品的规格参数页（如 `H100 规格`、`RTX 4090 参数`）——会锚定到单一产品页、无展开价值；搜厂商 / 产品的文档站、知识库、API、帮助中心入口（如 `NVIDIA developer documentation`、`{产品} official docs`、`{厂商} 技术手册`）——这类入口是高价值的成体系知识源。

### 证据链与写入纪律（脚本强制校验）

- 候选 URL 必须**逐字照抄**搜索结果——每次搜索的原始结果由系统自动留痕（PostToolUse hook），脚本会校验每个 URL 必须能逐字在留痕中找到，找不到的整条被拒绝
- 禁止凭先验知识补 URL；模型"记得"某个权威源时，必须先专门搜一次、让它的 URL 出现在结果里，才能收录
- 禁止对 URL 做任何"规范化"（补路径、换域名、去参数）——照抄原文
- 禁止截短 URL（取父路径/裸域名）——校验为边界匹配，截短不放行
- URL 尾部的 `#数字` 引用锚点是结果渲染记号，**照抄即可**——脚本会在输出 CSV 前确定性剥离；不要自行去掉（会被边界匹配判为截短拒绝）
- journal 的 query 照抄**实际发出的**查询词（脚本逐字比对留痕，不一致会被标注"证据缺失"）
- raw.json **直接 Write 一次性写完**——禁止自创脚本 / 中间文件组装（执行任何 Bash 如 `python build_xxx.py` 都会越界被权限白名单拦截弹窗）
- 只写契约字段，内部字段（如 `expected_type`）不写入
- **证据核对不手工做**——禁止用 grep/shell 循环/自创脚本等复合命令核对或重建（这是脚本的职责，越界命令会被权限白名单拦截弹窗）；调查/排查用 Read 工具
- 被拒条目不进清单——证据校验由脚本执行

### 提取规则

#### 粒度（如实标注，脚本不拦截）

- 每条候选声明 `granularity`：**合集级** / **单篇级**——仅作信息标注（后续站点/子站合并功能会用到），脚本不据此拒绝任何条目
- **单篇内容同样提取**（标单篇级）——单篇级在 `reason` 写明依据（如"单篇行业报告"）
- 同一来源同时有合集入口和单篇时：**优先收合集入口**，不收该来源的单篇（防重复）
- 仍然不收的只有三类：与领域无关的噪声结果、通用平台首页（见平台准入判据）、已收录过的重复条目

#### 语言版本偏好（同一内容只收一个版本）

- 同一来源的同一内容在结果中出现多个语言版本（如 `.../zh-cn/122240` 与 `.../en-nz/122240`，标题内容一致仅语言不同）时，按 **中文 > 英文 > 其他语言** 优先级只收一个
- 判定依据：URL 语言特征（`/zh-cn`、`/zh/`、`cn` 子域、中文标题）与内容语言；该来源没有中文版时收英文版，只有单一语言版本时照收
- 不同内容的独立页面不受影响；站点中文版内容不全时按实际存在的版本收
- 脚本会对最终清单做确定性审计（同域名剥语言码路径段后相同的组计数）——漏网会在 stdout 提示

#### 平台准入判据（通用平台不作为条目收）

- 知网、专利库、百科、标准平台首页等**跨领域通用平台**不提取为独立条目——无主题边界，URL 背后不是该领域的成体系内容
- 判据：条目的 URL 必须定位到该领域的内容（领域词条 / 分类页 / 带领域词的检索入口）；平台首页、平台根域名不收
- 平台的**领域专属入口**（专利库的该领域分类检索页、标准平台的该领域检索页）可收
- 通用平台对领域有价值的信息，写进该领域条目的 `description` 传递（如"全国标准平台可检索"）

#### 数据源类型（标签从词类词汇中选）

- `source_type` 从通用纪律“搜索词构造”的词类词汇中选取（组织形式词 / 体裁词 / 来源角色词），如“厂商文档”“行业标准”“公共数据平台”
- 一个词覆盖不了时，允许把两个词类词汇拼起来用（如“评测认证”）；不要往标签里加领域名（“航天行业标准”应归“行业标准”）；不另造同义新词——同义分裂会让体裁分布无法横向对比

### 失败路径（搜索工具异常）

搜索调用大面积失败（多数查询无有效结果返回）时：停止搜索，**不写 raw.json、不运行后处理**，**向用户显式声明失败状态**（`failed: true` + 简述），不伪造候选，如实报告"搜索工具异常，本次运行中止"。已预留的运行目录保持为空残留（可见可删，不影响下次运行）。

## 初始化 · 预留运行目录

流程开始时先执行（该 Bash 命令在权限白名单内，直接运行）：

```bash
python .claude/skills/autosource/scripts/postprocess.py --prepare
```

脚本创建 `outputs/run_{时间戳}/`（每次运行唯一，同秒自动加后缀）并打印完整路径——**照抄该路径**：阶段 5 用它写 raw.json，阶段 6 传同一路径收尾。该目录从此刻起就是本次运行的专属目录；若后续搜索失败中止，它保持为空残留（可见可删，不影响下次运行）。

## 阶段 0 · 领域拆解

将领域拆解为树状分类结构。

**禁止读取 outputs/ 下历史运行的产物**——历史清单是上轮结果的基线，照搬会继承上轮的遗漏与偏差；读取被权限拦截属护栏按设计工作，不是缺陷。

**拆解原则**：

- 层级清晰：上下级严格包含，同级互斥不重叠
- 符合领域常识：分类体系与该领域公认知识体系一致
- 符合业务逻辑：粒度匹配实际使用场景，不过细也不过粗
- 深度自适应：不同领域层级数可不同
- 覆盖完整：覆盖该领域主要方向，无明显遗漏
- 节点规模由覆盖完整性决定——不以搜索次数或运行时长为由合并节点（搜索成本由设计承担，不是拆解的约束）

### 节点搜索画像

完成分类树后，为每个叶子节点补充以下轻量信息：

- **节点边界**：说明该节点包含和不包含的内容，减少跑题和节点间重复
- **核心搜索词**：中文名、英文名、常见缩写或行业别名
- **相关来源类型**：该节点适合搜索的资料形态
- **相关来源角色**：可能发布该类资料的机构角色

搜索画像仅用于阶段 2/3 构造查询词和阶段 4 覆盖检查，不改变 `nodes` 字段契约，不要求将画像内容写入最终清单。具体机构仍由知识清单提供一部分，并通过搜索继续发现，禁止为填画像强行编造机构名称。

**完整性自检**：初步拆解后，再自问一遍——"这个领域公认的主要子方向，有没有被遗漏的？是否遗漏了相关配套生态？"显式列出可能被漏掉的方向（相关配套生态、某个细分技术、某类应用场景、某个层级），对照领域常识决定是否补入，再对照节点搜索画像逐节点复查，补上遗漏。

**输出**：将拆解结果以树形文字展示给用户。无需等待用户确认。

## 阶段 1 · 知识清单（零搜索）

基于领域知识直接列出该领域公认的**权威源清单**：

**列什么与列多少**：

- 结构：`{名称, 所属叶子节点, 预期体裁}`，**URL 留空待验证**
- 粒度：**合集级与单篇级都可列**——合集级列机构/知识体系（垂直门户按合集级）；公认的权威单篇载体（行业白皮书、关键标准文件、重磅报告等）也可列，声明 `granularity`（默认合集级）
- 规模：**尽量列全，不设条数上限**（产量优先；领域级权威源归到最相关节点名下）——验证不通过的条目由"未找到官方入口"处置自然过滤，**无需以搜索成本为由缩减清单**
- 生成顺序：按叶子节点逐项生成，先查看该节点的搜索画像，再从适用的来源类型和来源角色出发列出权威来源；不要先把全领域机构平铺后再被动分配节点
- 覆盖标记：对每个来源类型和来源角色标记为“已列”“已检查”或“不适用”。“已检查”表示考虑过但暂未找到明确候选，不等同于遗漏；不得为了填满维度强行编造机构名称；该标记不写入最终清单字段，也不改变 raw.json 契约
- 验证优先级：在流程内部可将候选来源标记为“核心”“重要”或“补充”，用于阶段 2 的验证调度；该标记不写入最终清单字段，也不改变 raw.json 契约

**准入判据**：条目必须指向该领域的内容（有主题边界）；跨领域通用平台的收与不收见通用纪律“平台准入判据”

**清单自检**：列完后按机构类型维度自问一轮——标准组织 / 行业协会 / 厂商文档体系 / 学术文献库 / 评测机构 / 开源生态 / 百科知识库 / 公共数据平台，以及中文生态的对应物，各类都列了吗？再按覆盖标记逐节点复查，确认各来源类型和来源角色的三态判定无遗漏。没有任何清单来源的节点在阶段 3 主要依靠节点搜索画像构造查询。这里的检查用于指导后续搜索，不要求为每个来源类型强行编造机构名称。

**预期体裁**：仅用于构造验证搜索词；最终 `source_type` 以验证时的实际形态为准，允许修正

**输出**：将清单与分类树一起展示给用户。无需等待用户确认。

## 阶段 2 · 验证搜索

阶段 0/1 的产出即本阶段输入：

```
领域词: 交换机
模型名: 当前实际使用的模型名（照抄进 raw.json 的 model 字段）
叶子节点:
  - 数据中心交换机
  - 企业园区交换机
  - ...
权威源清单:
  - {名称: IEEE 802.3 以太网工作组, 节点: 以太网标准(IEEE 802.3), 预期体裁: 行业标准}
  - {名称: Cisco Nexus 文档体系, 节点: 数据中心交换机, 预期体裁: 官方文档}
  - ...
```

- **查询词构造**：按来源实际情况自由组合（每词 2-4 个组件），组件池——**来源识别（必带其一）**：原名 / 英文名 / 缩写 / 别名；**入口意图**：官方文档 / 官网 / 入口 / 目录 / 数据库 / 标准列表 / 仓库；**辅助**：领域词、地域词和语言词。组合示例：`中国电子技术标准化研究院 交换机 标准`、`IEEE 802.3 Ethernet Working Group official`、`SONiC open source networking documentation`、`H3C 交换机 配置指南`。若清单项所属叶子节点有节点搜索画像，可按需加入该节点的核心搜索词、相关来源类型或来源角色，但不要求每次查询全部加入。
- **按来源语言搜索**（中文来源用中文词、英文来源用英文词）；来源语言不明或双语时，一个查询词内可同时带原名+英文名（如 `宁德时代 CATL 官网`），一次搜索覆盖两种语言——避免因语言猜错浪费本轮唯一一次搜索
- **清单每项只搜 1 次**：按“核心”→“重要”→“补充”的优先级处理；同一优先级内按原清单顺序搜索。失败即标记未验证，不在本阶段重试——换角度重试统一留给扩量轮（阶段 4）
- **通过标准（按条目粒度对应，搜到什么按什么收）**：目标始终是该机构的官方入口 URL；搜不到入口时按以下标准降级处理，扩量轮换"官网/官方文档"角度兜底。
  - 合集级清单项：搜索结果中出现该机构的**入口 URL**（文档门户/目录/列表页）即通过
  - 合集级清单项只搜到合集内**单篇载体**（PDF、单条 KB 等）：扩量轮换角度专找入口（如 `{机构名} documentation`）；仍找不到入口 → **以该单篇验证通过**，granularity 修正为"单篇级"，reason 注明"仅找到单篇载体，未找到合集入口"
  - 单篇级清单项：搜索结果中出现**该载体本身**即通过
  - 连单篇载体都没有 → 标记未验证，留待扩量轮换角度重试后按阶段 4 定案
- **通过后**：在**清单项内**填上 `category_path（完整路径）/ source_type / granularity / url / description / reason`（URL 照抄）；预期体裁允许按实际形态修正
- **未通过**：先标记 verified=false，不急于分类——扩量轮换角度重试后按阶段 4 定案
- 验证搜索时顺带发现的新源 → 全量提取（同样遵守粒度规则、平台准入判据与证据链约束）

## 阶段 3 · 增量发现

**搜索次数**：每节点 **8 次**搜索：

- **固定 4 次**（组织形式词中文/英文各 1 次，体裁词中文/英文各 1 次）：各取最贴节点的一个词
- **自由 4 次**（**仅中文搜索词**）：从角度池任选 4 个**本节点还没覆盖的角度**各搜一次

**角度池**（包括但不限于）：

- 学术类：论文 / 专利
- 组织形式类：列表 / 排名 / 数据库 / 标准 / 仓库 / 合集
- 体裁类：官方文档 / 手册 / 知识库 / 白皮书
- 数据类：数据集 / 开放数据
- 生态类：社区 / 博客 / 资讯平台
- 来源角色类：标准组织 / 监管机构 / 政府部门 / 行业协会 / 厂商 / 研究机构 / 大学 / 评测机构 / 基金会 / 公共数据平台

- **查询词构造**：围绕当前节点名称或节点搜索画像中的核心搜索词，组合一个发现型角度词；优先使用该节点适用的来源类型或来源角色。固定 4 次按中文/英文表达分别搜索；自由 4 次仅使用中文搜索词。以下约束仍适用：必须带发现型词汇，厂商 / 产品名的用法见通用纪律“搜索词构造”。不要要求每次查询同时包含所有组件，也不要把画像中的机构名称当作必须搜索的固定清单。
- **提取纪律**：全量提取、URL 逐字照抄、每条带 reason、遵守粒度规则与平台准入判据

## 阶段 4 · 覆盖评估与扩量（含清单定案）

**薄弱判定**：每节点统计候选数与体裁分布，并按 6 个核心来源维度核对覆盖情况（官方组织与标准 / 厂商与产品生态 / 学术与研究 / 开源与社区 / 数据集与公共数据 / 行业协会与市场信息），按以下标准判定薄弱节点：

| 情形 | 判定 |
|------|------|
| 候选少（0 条或明显少于同级节点）+ 清单项有未验证 | **薄弱**——扩量轮优先把未验证清单项验证掉，而非无目标的泛搜 |
| 候选少 + 清单项全验证通过 | **不薄弱**——权威源就这些，硬扩只会引入长尾噪声 |
| 体裁单一 | **薄弱**（补搜换体裁词） |
| 来源维度单一（条目明显集中于一个维度，如全是厂商文档） | **薄弱**——扩量轮按空缺维度定向补搜（用来源角色词构造查询）；以覆盖标记中的“不适用”为准，该维度对该节点明显不适用时不补 |

**未验证项定案**（扩量轮内，每轮换一个角度：中英切换 / 全称缩写别名 / `机构名+官网/官方文档`）：

- 换角度重试后仍搜不到该机构存在的**任何证据** → 疑似幻觉/过时 → **从有效来源中剔除**，note=“疑似无效机构”
- 能搜到该机构存在、但始终找不到官方入口 → 扩量轮（≤2 轮）结束仍失败 → **留在未验证清单**，note="未找到官方入口"

**终止条件**：所有节点非薄弱 **且** 清单项全部了结（验证通过或已定案）。**扩量轮上限 2 轮（全局）优先于薄弱判定**——某节点两轮后仍薄弱（如体裁客观上单一），视为收敛并如实报告，避免无限循环。

**扩量轮内的搜索范围**：① 未验证清单项换角度验证（每轮每项 1 次）；② 体裁单一的节点换体裁词补搜（每轮 ≤4 次）；③ 来源维度单一的节点按空缺维度补搜（每轮 ≤4 次，用来源角色词构造查询）。除这三类外不做其他补搜。

## 阶段 5 · 写入 raw.json（接口契约）

**把结果写入本次运行目录的 `raw.json`（用 Write 工具，路径 = 初始化 `--prepare` 打印的路径 + `/raw.json`，全部搜索完成后一次性写完整文件）**。写完文件后**不要结束回合**——立即执行阶段 6 收尾。

文件结构：

```json
{
  "domain": "交换机",
  "nodes": ["数据中心交换机", "以太网标准(IEEE 802.3)", "..."],
  "model": "当前实际使用的模型名",
  "knowledge": [
    {"name": "IEEE 802.3 以太网工作组", "node": "以太网标准(IEEE 802.3)", "verified": true,
     "category_path": "交换机-核心技术-以太网标准(IEEE 802.3)",
     "source_type": "行业标准", "granularity": "合集级", "url": "https://www.ieee802.org/3/",
     "description": "IEEE 以太网标准工作组官网", "reason": "清单验证通过，官方入口"},
    {"name": "某某机构", "node": "某节点", "verified": false, "note": "疑似无效机构"}
  ],
  "journal": [
    {"phase": "验证搜索", "node": "以太网标准(IEEE 802.3)", "query": "IEEE 802.3 Ethernet Working Group official", "results": 10, "extracted": 3}
  ],
  "sources": []
}
```

字段约束：

- `domain / nodes / model`：domain 为领域词、nodes 为全部叶子节点、model 为当前实际使用的模型名
- `knowledge`：node 必须在 nodes 中；verified=true 的项必须带齐 `category_path/source_type/url/description/reason`（category_path 用 `-` 连接完整层级路径，末段与 node 一致），`granularity` 可带（默认合集级）；verified=false 的项带 `note`（"疑似无效机构"或"未找到官方入口"）；被剔除的疑似无效机构也留在清单里（note 标注），供报告展示
- `sources`：仅增量发现条目，每条含 `name/category_path/source_type/granularity/url/description/reason`；granularity ∈ 合集级/单篇级（单篇级需在 reason 写明依据；缺省按合集级处理）；**不重复写已验证的清单项**（脚本自动并入）
- `journal`：每次搜索一条——`phase`（验证搜索/增量发现/扩量轮）、`node`、`query`（照抄实际查询词）、`results`（返回链接数）、`extracted`（提取候选数）
- 通用约束：name 和 url 不可为空；仅收录公开可访问的数据源；同一数据源只出现在一条分类路径下；分类路径术语统一；确保体裁多样性；通用平台规则见通用纪律“平台准入判据”
