# 规则强制力重构方案

> 阅读前提：docs/02-日志手册（本方案引用的决策出处）、docs/04-存储架构改造方案 §1.1。
> 定位：本方案不新增业务能力，只改变"规则存在哪里、由谁保证"。
> 状态：待评审。通过后按 §3 分期落地，每期独立验证、独立回退。

## 0. 结论

现行结构是：一份很长的提示词 + 一组脚本 + 一组权限配置。规则的"真话"写在提示词里，脚本与配置只承担流程执行。

由此形成闭环：发现漏洞 → 提示词是唯一可改的地方 → 追加一句话 → 提示词没有强制力，漏洞复现 → 再追加一句。`SKILL.md` 一个月内由 3700 字符增至 15800 字符，是该闭环的产物。`README.md` 结尾已写明"加在提示词上的约束，本项目默认认为拦不住"——原则早已成文，规则的存放位置没有变。

本方案只做一件事：**把规则的真话从提示词搬进代码与配置，提示词退化为入口说明。**

## 1. 目标与验收

**终局目标**（本期不追求达成，作为校验方向）
任一条规则，要么由机制保证（违反必被拒绝），要么被明确登记为"建议"。不存在第三种状态。

**本期验收基准**（用户确认，档 2「交付包可自证」）
每轮运行的产出物内附机器生成的验收单（含脚本指纹），使"这轮是否合规"可计算，不依赖人阅读报告判断。

**回归基线**
- 现有测试全绿（`README.md` 记录 249，实际收集 259，本期一并修正文档）
- 每期前后跑同一轮对照，基线取 2026-09-14 交换机轮（`outputs/交换机_2026-09-14-181607/`）

**约束**
CLAUDE.md 的简洁优先、避免过度抽象、精准修改；每期独立可验证、独立可回退。

### 1.1 生产级的口径（本方案的尺子）

"投入生产级使用"是方向，不是终点。本方案把它落成可验收的口径：

- **规则有执行点**：任一条规则，要么由机制保证，要么被登记为"建议"。
- **验收不靠人读**：每轮产出自带机器生成的核对材料。
- **环境可分离**：运行与开发分属两个目录，运行期禁读历史产物。
- **失败可见**：失败的轮次留下可读原因，不静默丢数据。
- **可交接**：不读讨论日志也能跑起来。

**本期补齐项**（在 §2 三个结构件之外，同属工程化落地，逐条确认做/不做）：

| # | 项 | 现状 | 建议 |
|---|---|---|---|
| 1 | 运行依赖集中说明（Python、宿主版本、MCP 装配） | 散落在 README、docs 与配置中 | 做 |
| 2 | 脚本版本号随产出落盘 | 无 | 做 |
| 3 | 失败轮次的留痕 | 无 | 做 |
| 4 | 入口文档：不读讨论日志也能跑起来 | 无 | 做 |
| 5 | docs/01 交付手册与实现校订 | 存在漂移 | 做 |
| 6 | 无人值守 / 并发 / 多人共享 | 无 | 本期不做（以手动触发起步，规模维持现状） |

**文档入库口径**（2026-09-15 确认）
`docs/` 默认不入库。契约类例外入库：`01-交付手册`、`03-待办账本`、`04-存储架构改造方案`、`06-本方案（本文件）`。讨论日志（02）、日报、`05-参考方案手册` 留本地。规则登记表属契约，落点为 skill 目录，必须入库——否则换机器后测试读不到它。

## 2. 三个结构件

### 结构件 A：契约单一来源

**现状**：同一套规则散落在五处——`SKILL.md`、`docs/`、MCP 工具说明、`.claude/settings.json`、测试。改一处其余不同步。测试以"抄录原文"的方式钉文本，既钉不住语义，又把错误事实一并钉死（实例：`tests/test_skill_structure.py` 中一条用例断言 settings 里不存在某条 deny 规则，而 `SKILL.md:98` 仍描述该规则在生效，二者相反）。

**做法**：新增一份机器可读的规则登记表（置于 skill 目录），每条规则一个条目：

| 字段 | 含义 |
|---|---|
| id | 人工命名的稳定标识；按**规则**建条，不按句子——同一规则在文档里出现多次只建一条 |
| summary | 一句话 |
| level | enforced（有机制 + 有机制类用例）/ enforced-no-test（有机制、无用例）/ advisory（只有文本） |
| impl | enforced 必填，带类型前缀：`python:文件:符号` / `settings:键路径` / `hook:` / `store:` |
| anchors | `SKILL.md` 章节标题 + 该条独有的一个短特征词。**不钉整句**——锚整句会在每次改句时全断，而改 `SKILL.md` 是本仓库最高频的动作 |
| test | 仅接受机制类用例。`tests/test_skill_structure.py` 属文本钉桩（断言的是文档原话），不计入——否则会形成"登记表从文本抄规则、用例从文本抄断言"的闭环，证明的不是机制 |

**配套测试**（`tests/test_rules_registry.py`，4 条）：id 唯一与等级/字段自洽；anchors 的章节与特征词都能在 `SKILL.md` 找到；impl 指向的目标真实存在；`test` 若填必须是机制类用例。**不做**关键词反向覆盖（实测两头都不可靠，见 §7）。

**不做的事**：不要求 `SKILL.md` 反向标注 id（避免污染提示词文本），漏登记风险由人工评审承担；不校验提示词句式与口吻——机械只能查引用完整性，语义判断留给人，工具最多输出一份"建议性条目写成了禁止口吻"的清单供人复核，不阻断。

**效果（2026-09-15 下调）**：登记表是**地图，不是闸门**——它拦不住任何人往 `SKILL.md` 里加句子。防追加真正的支点只有两个：登记纪律（人），以及规则有了机制之后、文本从义务句降级为说明句（机器）。原稿曾写"追加从此有成本"，复核后撤回。

### 结构件 B：执行单一入口

**现状**：同一批数据的收尾有两条路径，标准不同——命令行路径与程序内路径在配额、零提取、清单了结等校验上默认值相反，同一规则在两处各写一遍。

**做法**：校验收敛为一个入口，两条路径调用同一实现。允许保留的差异只有"输入来源"。

**验证**：同一批输入走两条路径，产出物逐字一致（对拍用例）。

### 结构件 C：拦在动作前 + 自证交付

**C1 禁读规则回归（运行环境 / 开发环境分离）**

禁读规则早先存在（`deny Read(outputs/**)` + `deny Glob(outputs*)`，按转录实证的两条自锚定通道设置），2026-09-08 移除。移除原因不是规则不对，而是**静态规则分不清运行态与复盘态**，一刀切会拦住开发复盘。

分离环境即可恢复该规则，且不需要钩子：

- **运行环境**（本项目目录）装那两条 deny；**开发环境**不装，照常读产物。配置随目录走，不存在"忘记切换"。
- 可行性依据（已核实）：运行期间模型不需要读 `outputs`——阶段 0/2 对 `outputs` 的操作是 **Write** `manifest.json`（写不受禁读影响）；阶段 7 Read 的对象是 skill 目录下的报告模板，不在 `outputs` 内；阶段 7 的 `--rename-report` 由 Bash 调脚本执行，脚本的读取与模型的 Read 工具是两条通道。
- 附带收益：静态规则只作用于 Read/Glob 工具，**不会误伤 `--rename-report`**；钩子方案必须为它另开白名单。
- 已知边界：`Bash(cat outputs/...)` 或自写脚本读取，静态规则拦不住。钩子方案同样拦不住。本期接受，登记挂账。
- 文本同步：`SKILL.md:98` 现描述与配置事实相反，本件落地后改为如实表述。

**备选（本期不采用）**：PreToolUse 钩子 + 运行态标记文件（本机 Claude Code 2.1.226 实测可拦截）。成本更高：需写运行态标记、设过期兜底、为 `--rename-report` 开白名单，Bash 通道仍为字符串粗判。仅当"运行与开发必须在同一目录"时启用。

**C2 自证交付包**

- 验收单（置于运行目录，与两件交付物并列）：来源条数与清单条数、证据校验结果分布、零提取记录及其理由、清单了结对账结果、生成时间、脚本版本。
- 指纹：对交付物文件计算哈希，写入验收单。
- **边界（重要）**：哈希只能让事后改动可见，不能防伪造——模型自身也能计算。要达到不可伪造，需把锚点放到模型写不到的地方；本期不做，登记挂账。
- 缺陷策略（用户确认）：一律产出，缺陷在验收单中如实标注，不拒绝产出。

## 3. 分期

每期单独可验证、可回退。顺序不可颠倒的理由见第 5 期。

| 期 | 结构件 | 一句话 |
|---|---|---|
| 1 | A | 建立登记表，产出首份"多少条有机制、多少条只是建议"的报表 |
| 2 | C2 | 验收单与指纹进入运行目录 |
| 3 | C1 | 两条禁读规则装回运行环境（配置改动，成本极低，可插到任意位置） |
| 4 | B | 两条路径收敛为一条 |
| 5 | A | 文本与文档收口（删减、测试清理、依赖说明、入口文档） |

**第 1 期 · 规则登记表**（2026-09-15 完成）
- 动手范围：新增 `.claude/skills/autosource/rules.json` 与 `tests/test_rules_registry.py`，不改任何现有文件、不改行为。
- 结果：35 条规则——**enforced 20 / advisory 15**。即后面站着执行点的 20 条，与只有文本的 15 条。
- 口径修正（同日）：初版把 4 条靠权限白名单的记为 enforced-no-test；查证后降为 advisory——白名单对越界命令的效果是**弹窗询问**，而弹窗意味着运行停下来等人，与「流程中间没有交接停靠点」冲突（`SKILL.md:49` 自己写的"拦截弹窗"与这条通则互相矛盾）。**靠询问的拦截不算机制。**
- 验证：263 个测试全绿（259 + 新增 4）；行为与基线一致。
- 回退：删除两个新增文件。

**第 2 期 · 自证交付包**（2026-09-15 完成）
- 动手范围：`fold()` 收尾时在运行目录根写出 `{目录名}_运行验收单.json`；CLI 兼容路径（直调 run_pipeline）不产出它。
- 定位（2026-09-15）：**验收单**，不计入交付物——根目录 = 两件交付物（清单 / 报告）+ 一件验收单；排障材料仍全部在 intermediate/；命名与其它产物同前缀（`{目录名}_运行验收单.json`，2026-09-15 由 `运行核对.json` 改名）。
- 内容：来源条数与拒绝明细、清单声明与核对记录对账、零提取次数与理由、每节点搜索次数与配额、脚本指纹、生成时间——全部由脚本从 store 与流水线 summary 直接算出。
- 边界：只记录事实、不做拦截；写不出来时兜住异常、打警告、**不影响交付**（自证工具不得成为新的报废来源）。
- 口径修正：原计划的交付物指纹（sha256）与 `--verify` 开关经评审砍掉——它们防的是"文件事后被改"，而记录里没有这类事故，且会改文件的模型自己也算得出哈希。留下的是每一条都能指到真实事故的数字。
- 验证：266 个测试全绿（263 + 新增 3）；待真跑一轮复核数字与清单行数是否一致。
- 回退：移除生成逻辑。

**第 3 期 · 禁读规则回归**
- 前提：运行环境与开发环境分离已就位。
- 验证：运行环境中，模型试图 Read/Glob `outputs` 被拦；同一目录在开发环境中照常可读；一轮完整运行不被这两条规则打断（重点确认 `--prepare` 写入、阶段 7 报告写入与重命名均正常）。
- 回退：移除那两条 deny。

**第 4 期 · 单一入口**
- 验证：对拍用例通过；跑一轮，两条路径产出物一致。
- 回退：保留原两套实现，撤回调用合并。
- 预期副作用：命令行路径启用校验后，此前被掩盖的缺失会暴露（这是本期目的），预计有一轮"变红"。

**第 5 期 · 文本与文档收口**
- 动手范围：删除已被机制接管的句子；改写或删除"抄录原文"类测试；修正 `README.md` 测试数；§1.1 补齐项（依赖说明、脚本版本、失败留痕、入口文档、交付手册校订）。
- 验证：与第 4 期结果对照，行为无差异；不读讨论日志也能按入口文档跑通一轮。
- 验证：与第 4 期结果对照，行为无差异；测试数下降但全绿。
- 前提：必须在前四期完成之后执行。顺序颠倒即为先撤兜底、后补机制，是本项目已发生过的失败模式。

## 4. 不做的事

目录迁移、状态机、并发、多用户平台化。以上与本方案的病根无关。

不引入代码生成工具链（不把 `SKILL.md` 做成生成物），判据见 §6。

## 5. 已确认的决策与出处

| 事项 | 结论 | 出处 |
|---|---|---|
| 规则存放位置 | 接受重构，判据是"对应哪个机制缺口"，而非"代码能否正常运行" | 用户确认 |
| 本期结构件 | 三件（契约单一来源 / 执行单一入口 / 拦在动作前 + 自证交付）；原"五阶段小修"降为其结果 | 用户确认 |
| 验收基准 | 档 2 交付包可自证 | 用户确认 |
| 自证形态 | 另附验收单 + 指纹 | 用户确认 |
| 契约形态 | 手写 + 一致性校验，不做生成 | 用户确认 |
| 文本类测试 | 允许改写与删除 | 用户确认 |
| 缺陷策略 | 一律产出、如实标注 | 用户确认 |
| 禁读方案 | 静态规则 + 运行/开发环境分离，不采用钩子 | 用户确认，依据见 C1 |
| 运行期间模型是否需要读 outputs | 不需要（三条依据见 C1） | 本机代码核实 |
| 禁读规则原始设置与移除原因 | `deny Read(outputs/**)` + `deny Glob(outputs*)`；移除因静态规则无法区分运行态与复盘态 | docs/02 2026-09-08 |
| 宿主钩子能力（备查） | PreToolUse 可真正拦截（退出码 2 或 permissionDecision: deny）；matcher 仅匹配工具名；钩子无法获知当前激活的 skill | 本机 Claude Code 2.1.226 核实 |
| 文档入库口径 | `docs/` 默认不入库；01、03、04、06 四份契约类例外入库 | 用户确认（2026-09-15） |

## 6. 本方案何时应被推翻（判据）

写在这里，供后续反驳本人判断，而不是事后辩解。

| 结构件 | 推翻条件 | 那时的做法 |
|---|---|---|
| A | 登记表条目多到无人通读，或改一条规则要同步超过两处 | 改为从执行点反向生成登记表；或砍掉规则本身 |
| B | 两条路径的差异无法收敛到"仅输入来源不同" | 说明它们本就不是同一件事，应各自定义契约，而非强行合并 |
| C1 | 运行与开发无法分离到不同目录 | 启用备选的钩子方案 |
| C1 | 静态规则被绕过（Bash 通道）且实际造成自锚定事故 | 升级为钩子方案，或引入沙箱级只读管控 |
| C2 | 验收单的误报率高于可接受水平（以 09-14 轮做原型比对得出） | 降级为仅记录、不断言 |

## 7. 待验证事项（客观事项，不阻塞本方案）

- 报告引用与清单比对的误报率（决定 C2 的断言强度）
- `README.md` 测试数漂移（写 249，实际 259）
- 关键词反向覆盖法已实测否决：漏 10+ 条真规则（"只…/不…/须/不要/固定"整类否定与限量句式），多算 14 条非义务叙述，且判不了肯定/否定（`SKILL.md:220`「不是必须」）。若第 5 期要重建闸门，不能再用关键词法
- 白名单外的一切操作从"询问"改为"拒绝"（不弹窗）——做完这条，被降级的 4 条才会真的变成机制；建议归第 3 期（该期本就在动权限配置）
- Bash 通道绕过的实测确认
- 挂账事项（Bash 通道、指纹不可伪造、无人值守路径）落地时登记进 docs/03-待办账本
