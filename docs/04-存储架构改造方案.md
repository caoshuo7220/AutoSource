> 状态：**已实施并通过端到端验收（2026-08-31）**。本文档为设计依据归档；现行流程以 SKILL.md 为准，实施与验收记录见 docs/02 讨论日志。

> 阅读前提：docs/02 日志手册（讨论日志；截断事故分析过程见本方案第 1 节引用的转录实证）。

## 1. 背景与根因

### 1.1 事故记录

2026-08-28 硬件总线接口规范轮（085759）：模型采用"先 Write 空骨架（44KB、sources:[]）+ Edit 分块追加"策略——Edit 被 outputs 权限拦截（该目录只放行 Write，Edit 底层读被 deny 拦死）——被迫退回单次 ~260KB（模型自估）大写入，生成卡 13 分钟，用户打断；打断时 raw.json 仍是 `sources: []` 空骨架，脚本无法区分"空骨架未完成"与"真 0 条"，静默丢全量，靠用户手动指挥分卷写入才救回。共犯链：**Edit 墙逼出单次大写入策略（结构性共犯）；单次大写入顶到模型输出上限边界（主犯，交换机轮 9 次撞墙证据见 1.2）**。

### 1.2 两轮转录逐条对比（实证，勿再复查结论）

| | 交换机轮（114546，813 条） | 总线领域轮（085759，840 条） |
|---|---|---|
| 表面结果 | "正常"完成 | 中途被用户打断，手动救援 |
| 真实写入过程 | 骨架检查点 15 次；18 分钟内宣告"写完整版" 9 次、每次只落盘 38KB 骨架；最终一次 218KB 完整写入侥幸成功 | 骨架 1 次（44KB）；试 Edit 分块追加被 outputs 权限拦截；被迫单次 ~260KB 大写入卡 13 分钟；用户打断 |
| 模型思考块证据 | 自知顶在输出上限、**主动压缩输出**（"minimal JSON, entries on single lines"） | 自估 ~260KB、决定"一次 Write，失败再适应" |
| 结论 | **两轮同处边界掷硬币区**（实测边界 218-260KB：218 压线成功、该轮自身 9 次 >250KB 尝试全部落空；总线 ~260KB 结局未观测——用户打断） | 同左 |

> 口径注：括号内 813/840 为**最终收录数**（候选经去重与证据移除后）；两轮 raw.json 的 sources 数组本体分别为 767 条（+56 清单并入 = 823 候选）与 807 条（+37 清单并入 = 844 候选）。

### 1.3 三层反模式诊断（根因，不只是"写入太大"）

1. **模型用 Write 倾倒大文件**——违反函数调用式小批量输出的行业标准模式
2. **单会话累计处理 250 次搜索结果 ≈ 40-50 万 token**（模型自估累计量）——违反有界工作集
3. **证据校验拖到收尾才爆**——违反入库时校验（ETL 数据质量门）

截断只是第 1 层的最表面症状。本方案以"LLM 只做窄工具调用 + 小批量结构化输出；持久化、校验、对账全部由确定性代码持有"为总原则，同时解决三层。

## 2. 方案总览

```
初始化 --prepare → 预留 run_dir（不变）
阶段 0-1：拆解 + 知识清单 → Write manifest.json {domain, nodes, model, knowledge 声明版}（~几 KB，整轮唯一一次 Write）
阶段 2：每 ~10-15 次验证搜索 → record_search(批次) + record_knowledge(清单核对批次，与搜索日志同节奏)
阶段 3：基底 16 次完成时 → record_search(该节点 16 条搜索记录) + record_sources(该节点增量条目批次)；扩充每批 4 次再落一次
阶段 4：扩量按节点收敛，每节点完成时 → 同上批量 record；清单定案项 → record_knowledge；coverage() 按需查缺失
阶段 5：清单了结自检（应录 N vs 已录 M，缺录补 record_knowledge）——manifest 无需重写
阶段 6：finalize(run_dir) 一次性折叠（复用 postprocess 引擎，含清单了结对账）→ 展示 stdout → 写分析报告（不变）
```

- 模型最大单次输出：manifest ≤15KB、record 批次 15-25KB（一个节点的条目量）——离截断边界约 10 倍
- 记录粒度 = 自然工作单元（节点），非每次搜索——group commit 模式（数据库 WAL / Kafka 批量冲刷同款）：逐搜索粒度一轮 ~500 次调用，多付 +20-30 分钟墙钟与 ~5-10 万封套 token，无对应收益；批量后一轮 ~30-40 次调用
- store = JSONL 追加日志（事件溯源）；脚本持有全部数据文件
- raw.json 契约**取消**（sources/journal 走 store；domain/nodes/model/knowledge 走 manifest）
- 上下文注记：条目一旦写出就会留在会话历史里，store 不削减运行中上下文——它保证的是**压缩安全**：会话压缩（compaction）后模型可以放心忘掉已写内容，靠 coverage() 与 store 继续正确工作；旧契约下压缩 = 丢数据。**边界：压缩后可恢复的只是条数级状态（某节点还缺多少条）；角度级状态（还剩哪个搜索角度没做）不可恢复——角度多样性脚本校验已裁决不做（2026-08-31），该缺口以散文层治理维持，不属于 coverage 职责**
- 证据 hook、权限白名单、报告统计注入、分析报告模板——全部不动

## 3. 组件规格

### 3.1 store.jsonl（脚本持有，模型不可见）

追加日志，每行一条，脚本盖时间戳（模型无时钟）：

```jsonl
{"type":"source","node":"数据中心交换机","name":"...","category_path":"...","source_type":"...","granularity":"合集级","url":"...","description":"...","reason":"...","ts":"..."}
{"type":"search","phase":"增量发现","node":"数据中心交换机","query":"...","results":10,"extracted":3,"ts":"..."}
{"type":"knowledge","node":"以太网标准","name":"IEEE 802.3 工作组","verified":true,"category_path":"...","source_type":"...","granularity":"合集级","url":"...","description":"...","reason":"...","ts":"..."}
```

- **store 承载三类记录：增量发现条目 + 搜索日志 + 清单核对结果**（2026-09-08 架构修订，见 §3.2 record_knowledge 与 §3.3）
- 单次追加原子（append + flush），崩溃最多丢最后一个批次

### 3.2 MCP 工具四件套（stdio 服务，.mcp.json 注册，会话启动自动拉起）

**`record_sources(run_dir, entries[]) → {accepted, skipped, rejected:[{index, name, url, reason}]}`**

- 入库即验（逐条）：name/url 非空；url 走现有 `contains_bounded` 证据校验（复用，含 `#` 豁免、`?` 严格）；granularity ∈ 合集级/单篇级（缺省合集级）
- 幂等：**裸 URL 精确相等**才跳过并计数（不归一化——见 8.1 裁决理由；真正去重仍由 finalize 域名+名称联合完成）；实现注记：查重基于服务进程内存 URL 集合（启动时全量扫描 store 建 set，~800 条级，无需索引）
- 被拒条目逐个返回原因，其余照常入库——单条被拒不影响批次
- **只收增量发现条目**——知识清单不进此通道（见 3.3）：清单未验证项本就没有证据，走"入库即验"会被当坏数据拒掉

**`record_search(run_dir, entries[])`**——entries 为搜索记录数组，每项 `{phase, node, query, results, extracted}`

- 逐条 query 逐字比对证据留痕（现状机制：比对在 finalize 收尾折叠时执行），不在则标注"证据缺失"（同现状，不拒绝）
- 批量粒度：阶段 2 每 ~10-15 次验证搜索一批；阶段 3/4 每节点完成时一批（该节点全部搜索记录）

**`record_knowledge(run_dir, entries[]) → {accepted, rejected:[{index, name, reason}], unmapped}`**（2026-09-08 架构修订新增）

- 清单核对结果随验证过程落库——废除"会话暂存 + 阶段 5 一次性转写 manifest"（214051 事故实证：手工转写 65 条 JSON 漏写 60 个 verified 字段，且与压缩丢失风险同源）
- 每项 `{name, node, verified, category_path?, source_type?, granularity?, url?, description?, reason?, note?}`：name/node 必填；verified=true 必带 url 且走证据链入库即验（当场拒绝+原因，可修正重传）；verified=false 带 note、不带 URL、不查证据
- 同名重录 = 状态更新（append-only，折叠按 name 取末次记录）；source_type 入库即归一（canonical + raw 留痕），表外词进 unmapped
- 批量粒度：阶段 2 每 ~10-15 项一批（与 record_search 同节奏）；阶段 4 扩量轮定案项一批

**`coverage(run_dir) → 每节点 {node, recorded, extracted, missing}`**

- 只读计数：recorded = store 中该节点 source 数；extracted = 该节点 journal 提取数之和；missing = max(0, extracted - recorded)
- **只测缺失，不测薄弱**（体裁/来源维度单一由模型在会话内判断，依据是它刚提取的内容；角度多样性脚本校验原为待办账本的独立挂账项，2026-08-31 裁决不做，不混入）

**`finalize(run_dir) → stdout 统计汇总（同现状收尾输出）`**

- 一次性折叠：读 store + manifest → 组装等价 raw 结构 → 复用现有 postprocess 全链路（证据终检/清单并入/去重/CSV/stats/溯源/搜索日志/目录重命名/归档）——**逻辑一行不改，只换入口**
- **防截断哨兵（保留）**：store 中 source 总数为 0 且 record_search 提取合计 > 0 → 拒绝折叠，显式报错"来源未入库，疑似违约未调用 record_sources"——模型若无视新契约、攒到最后直接 finalize，不会再静默丢数据
- **清单了结哨兵（2026-09-08 新增）**：声明清单项在 store 中无核对记录 → 拒绝折叠并点名（漏调 record_knowledge 同样响亮失败）；2026-09-08 前归档的 manifest 最终核对态（带 verified 字段）走旧路径兜底，历史归档可复盘
- manifest 缺失/损坏 → 显式失败，目录不重命名
- 收尾失败时不重命名目录、不清理——可安全重跑（幂等）

**记录粒度与开销（group commit）**：所有 record 调用按自然工作单元批量——阶段 2 每 ~10-15 次搜索、阶段 3/4 每节点完成时，一轮 ~30-40 次调用（逐搜索粒度约 500 次，多付 +20-30 分钟墙钟与 ~5-10 万封套 token，无对应收益）。批次大小 = 单节点条目量（30-60 条 ≈ 15-25KB），与总线领域轮实证的分卷规模（100 条/卷、8/8 全成）同量级。代价：会话在节点中途崩溃最多丢该节点未冲刷的半批——hook 留痕不受影响、可重建，本项目零中途崩溃案例，风险敞口可接受。

### 3.3 manifest.json（模型 Write 一次：阶段 0-1 声明版——2026-09-08 修订）

```json
{"domain":"交换机","nodes":["数据中心交换机","..."],"model":"当前实际模型名",
 "knowledge":[
   {"name":"IEEE 802.3 工作组","node":"以太网标准","预期体裁":"行业标准"},
   {"name":"某机构","node":"某节点","预期体裁":"官方文档"}
 ]}
```

- **阶段 0-1 写声明版（整轮唯一一次 Write）**：knowledge 各项只含 name/node/预期体裁（URL 留空待验证）——清单声明是确定性输入，落盘在确定性快照里
- **清单核对结果不进 manifest**（2026-09-08 修订）：随验证过程经 record_knowledge 分批落库，收尾折叠时由脚本按 name 对账并入——原"阶段 5 整体 Write 重写最终核对态"废除（214051 事故：手工转写 65 条 JSON 漏写 60 个 verified 字段，finalize 如实报 0/65 后模型违规手动收尾；转写环节与压缩丢失风险同源，一并根治）
- **若需修正必须整体 Write 重写，禁止 Edit**（outputs 目录 Edit 被权限拦截，总线领域轮实证——Edit 墙是 08-28 事故的共犯）

### 3.4 postprocess.py 引擎化

- 拆为可导入函数模块（证据校验/清单并入/去重/CSV/stats/溯源/折叠）+ 原 CLI 入口保留
- CLI 行为不变（现有测试全过）；旧 raw.json 路径保留兼容（历史轮次/测试）
- MCP 服务 import 这些函数——无逻辑重复

## 6. 验收标准（不变量层级）

1. 交付物四件套（清单 CSV/stats/分析报告/搜索日志）内容语义与旧契约完全一致（逐列口径不变）
2. 入库即验：无证据 URL 当场拒绝并反馈原因，finalize 零新增拒绝
3. 截断场景（store 空 + 提取 > 0）→ finalize 拒绝并显式报错，目录不被重命名
4. 旧契约兼容：无 store/manifest 的旧 raw.json 走 CLI 结果不变
5. 单次模型输出上限：manifest ≤ 15KB（含 knowledge 最终态）、record 批次 ≤ 30KB（一个节点条目量，离截断边界约 10 倍余量）
6. 现有测试 + 新增测试全过
7. 证据 hook/权限白名单/报告统计注入/报告模板无改动

## 8. 裁决记录（实施时不重新决策）

### 8.1 已裁决并纳入方案

| 评审点 | 裁决 | 理由 |
|---|---|---|
| raw.json 五块字段归属 | 瘦身不取消：sources/journal→store；domain/nodes/model/knowledge→manifest（清单声明于阶段 0-1、最终核对态于阶段 5 整体 Write 重写） | finalize 的目录命名/空节点检测/清单并入/stats 全靠元数据；清单声明是确定性输入，不进事件流 |
| manifest 重写方式 | 整体 Write、禁 Edit | Edit 在 outputs 被权限拦截（总线领域轮实证） |
| 幂等键 | 裸 URL 精确相等 | 归一化会合并 query 差异（语言版本偏好规则下是不同内容）；`?` 严格是 6064593 纪律；去重键形式化是 P-007 账本项 |
| coverage 范围 | 只测缺失 | 薄弱判定是语义判断，留模型；角度多样性校验原为独立账本项，2026-08-31 裁决不做 |
| finalize 性质 | 一次性折叠，不做增量 postprocess | 聚合操作留收尾；"边收边跑"仅指 record（追加）+ coverage（只读） |
| run_dir 传参 | 工具参数，照抄 --prepare 路径 | 与现状 postprocess 收路径同构 |

## 10. 历史教训映射（实施时对照）

- **Edit 墙**（总线领域轮）：契约只允许 Write
- **断点事故**（平板电脑轮）：流程线性不变，finalize 就是收尾最后一步，无交接
- **提示词约束不可强制**：模型可能违约不调 record_sources → finalize 哨兵兜底，失败响亮
- **build_raw.py 事件**：模型禁止任何自创脚本组装——record 工具就是组装环节的脚本化归位
- **无人值守容错**：单条被拒不阻断批次；finalize 永不因被拒中止（隔离计数，现状机制不变）
