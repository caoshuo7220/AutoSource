# AutoSource 问题记录手册

> 用途：逐项核对 AutoSource 的实际设计是否服务于“发现公开知识源”的上游任务；记录讨论结论，而非预设现有方案有问题。
>
> 边界：本手册只讨论发现阶段——识别并输出可供下游消费的来源 URL 及必要描述。下载、页面遍历、解析、清洗、抽取等抓取细节属于下游，不在本手册范围。

## 已确认的产品定义

- **目标**：自动发现某个领域内公开的互联网知识源，并输出来源清单，供下游任务按 URL 抓取具体内容。
- **发现对象**：不局限于数据集；包括官方文档、产品说明、技术手册、知识库、开放标准、论文、API 文档、帮助中心等。
- **准入边界**：资源应公开可访问。该条件是发现阶段的筛选前提，不应展开成下游抓取策略。
- **关注重点**：是否找到了应覆盖的来源、来源是否相关、重复来源是否被合理归并、输出是否足够让下游识别来源。
- **不讨论**：如何抓取、抓取哪些页面、反爬应对、内容解析、清洗与入库。

## 本手册如何记录问题

每个问题使用下列字段：

| 字段 | 含义 |
| --- | --- |
| 编号 / 状态 | 便于追踪；状态为“待核查 / 讨论中 / 已决定 / 暂缓”。 |
| 问题 | 需要作出的产品或架构判断。 |
| 已知事实与证据 | 来自需求、代码、测试或实际运行结果；没有证据时明确标注。 |
| 影响 | 不解决会造成的发现结果问题。 |
| 待讨论 | 需要先达成一致的判断点。 |
| 结论 | 讨论后填写；未达成一致时保持为空。 |
| 后续动作 | 只有结论明确后才添加实施或验证动作。 |

## 关于“来源元数据”

这里的元数据不是“如何抓取”的提示，也不是下游抓取清单。它只是在一条来源 URL 旁，保留**识别、展示、去重和筛选该来源所必需的描述**。

建议先按最小集合理解，是否保留由后续讨论决定：

| 字段 | 示例 | 用途 |
| --- | --- | --- |
| `url` | `https://docs.example.com/product/` | 下游任务的输入和来源唯一定位。 |
| `title` | `Example Product Documentation` | 让人和程序识别来源名称。 |
| `source_type` | `official_docs`、`manual`、`standard`、`paper` | 区分知识源类别，便于筛选和评估覆盖面。 |
| `scope` | `Example 产品的开发与运维文档` | 说明该 URL 覆盖的主题或内容集合。 |
| `publisher`（可选） | `Example Inc.` | 识别发布主体，辅助判断权威性与去重。 |

明确**不属于发现阶段输出**的内容：抓取方式、抓取深度、应抓页面列表、解析规则、反爬策略、登录方式、清洗规则等。

## 问题清单

### P-001：项目概念是否仍被“数据集发现”限制

- **状态**：待核查
- **问题**：当前术语、分类、搜索策略和筛选标准，是否把“数据源”狭义地实现成数据集，而未覆盖广义知识源？
- **已知事实与证据**：产品目标已明确为公开知识源发现；尚未完成对现有实现、测试和输出格式的核查。
- **影响**：如果项目仍以数据集为中心，官方文档、手册、标准和产品知识库等高价值来源可能根本不会被发现，或被错误过滤。
- **待讨论**：哪些来源类型是第一阶段必须支持的；哪些类型可以暂缓。
- **结论**：待讨论。
- **后续动作**：核对现有分类、提示词、过滤规则、结果字段和测试样例。

### P-002：发现结果的最小粒度尚未确定

- **状态**：讨论中
- **问题**：一条“数据源”究竟代表站点/域名、内容集合，还是单篇页面/单个文件？
- **已知事实与证据**：下游按 URL 抓取；发现阶段的对象可以是文档库、某版本手册集合、标准库，也可能是单篇 PDF 或页面。
- **影响**：粒度会直接影响搜索词、去重方式、输出数量和下游入口。
- **待讨论**：是否采用“三层都有、以内容集合级为主”的模型；如果采用，三层之间如何关联和去重。
- **结论**：待讨论。
- **后续动作**：确定后再固定输出结构与去重规则。

### P-003：输出描述应服务于来源识别，而非下游抓取

- **状态**：已初步澄清
- **问题**：发现任务需要输出哪些最小字段，才能让下游根据 URL 使用结果，同时不侵入下游职责？
- **已知事实与证据**：已明确不需要抓取提示、页面清单、抓取深度或解析规则；上文列出了仅用于来源识别的候选字段。
- **影响**：字段过少会使结果难以判断与去重；字段过多会把下游责任混入上游，增加不必要复杂度。
- **待讨论**：`title`、`source_type`、`scope` 是否为必填；`publisher` 是否暂定为可选。
- **结论**：暂定以 `url` 为必填，其余字段在讨论后确定。
- **后续动作**：待 P-002 的粒度结论确定后，一并定稿。

### P-004：如何定义“发现得足够好”

- **状态**：待讨论
- **问题**：自动发现无法证明覆盖互联网全部资源时，用什么标准评价结果是否足够完整、相关和可信？
- **已知事实与证据**：目标是产出供下游消费的候选 URL；目前尚未确认项目是否已有覆盖率、重复率或人工抽检机制。
- **影响**：没有明确评价标准时，搜索轮次、分类扩展和过滤规则无法稳定迭代。
- **待讨论**：是否先以“各必需来源类型均有候选 + 人工抽检相关性 + URL 去重”为第一阶段标准，而不追求不可验证的全网穷尽。
- **结论**：待讨论。
- **后续动作**：结合现有 `stats` 与测试机制核查后再决定。

### P-005：关键确定性环节未代码化，由 Claude 手工执行

- **状态**：已决定
- **问题**：CSV 规范化生成、`stats` 写入、中间文件清理等确定性环节，应由代码保证，还是继续交给 Claude 手工执行？
- **已知事实与证据**：全仓库无生成 CSV / 写 stats 的代码，`postprocess.py` 只产出 `clean.json`；`SKILL.md` Step 5/6 为自然语言指令。实测：2026-08-12 运行无 `stats.json`；2026-08-13 的 `stats.json` 中 `"model"` 为占位符原文，字段与脚本 stdout 口径不一致（脚本算出的去重数 / 无效 URL 丢失）；`clean.json` 导出后即删，无法审计 CSV 是否忠实反映脚本过滤结果。
- **影响**：产出格式、完整性、可审计性均依赖 Claude 每次正确执行，不可复现；违反 NFR 5.5（效果数据）与可迭代性要求。
- **待讨论**：将 CSV 导出 + stats 写入下沉进脚本（用 `csv` 模块保证 BOM 与转义），Claude 只负责发现与拆解；是否保留中间产物用于审计。
- **结论**：按"确定性逻辑代码化、LLM 只做语义推理"原则，全部下沉进 `postprocess.py`：脚本负责时间戳与目录命名、去重、CSV 导出（csv 标准库 + UTF-8 BOM）、stats 计算与写入（含空节点检测、处理耗时）、raw.json 清理；Claude 只产 raw.json。中间产物默认删除，提供 `--keep-raw` 参数保留供审计。
- **后续动作**：已完成——`postprocess.py` 重写 + 18 个单元测试 + SKILL.md 流程同步（2026-08-13）。

### P-007：后处理健壮性不足——脏数据即崩溃，去重口径有盲区

- **状态**：讨论中
- **问题**：后处理如何对不完整输入容错？去重键是否需要归一化？
- **已知事实与证据**：`postprocess.py:25` 直接下标取 `name` / `url`，缺字段即 `KeyError`、整批中断（实测），`process()` 无任何容错。去重 `_domain()` 用完整 `netloc`，`www` / 非 `www`、大小写、末尾斜杠、名称未归一化会漏合（实测 `nvidia.com` 与 `www.nvidia.com` 被留为两条）。次要项：串行校验慢（31 条实测 143s）、GET 分支连接未 `close()` 泄漏、重试无退避。
- **影响**：脏数据可致整次运行异常无产出（违反 AC-1）；去重存在盲区（NFR 5.2）。
- **待讨论**：对缺 `name` / `url` / 空值记录跳过并计数上报；去重键做 host 归一化（去 `www.`、小写化）；是否并发化校验。
- **结论**：待讨论。
- **后续动作**：结论确定后修 `postprocess.py` 并补测试。

### P-008：产量不达标，且流程步骤缺乏强制保证

- **状态**：讨论中
- **问题**：如何稳定达到 AC-2（≥50 条）？哪些“逻辑步骤”应从提示词下沉为代码 / 脚本兜底以保证可复现？
- **已知事实与证据**：2026-08-13 / 2026-08-12 产出 31 / 10 条，均 < 50，忠实校验后 08-13 降至约 27。领域拆解、扩量终止（`autosource-search/SKILL.md:64-66`）、无结果降级、写 stats、清理中间文件全为提示词、无强制。实测两次运行质量与格式悬殊：08-12 严重违反“禁止产品名”规则（满是 NVIDIA 产品页 / 对比）且无 stats，08-13 相反偏榜单。
- **影响**：违反 AC-2；可复现性差。
- **待讨论**：对扩量给出可量化的最低产出 / 收敛保证；能代码化的（终止阈值、降级重试次数、stats、清理）尽量代码化；“禁止产品名”等硬约束做成搜索层检查项。
- **结论**：待讨论。
- **后续动作**：评估产量与扩量策略。
